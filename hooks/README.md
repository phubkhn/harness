# hooks

Runtime enforcement for `rules/protected-paths.yaml`. A hook must not keep its own copy of a rule — it reads the rule file at run time.

## Cross-platform: `run-hook.cmd`

Every hook script (`check-protected-paths`, `check-agent-manifest`, `session-start`) uses a file name **with no extension** — this is not a missing `.sh`, it is on purpose: Claude Code on Windows has an auto-detect feature that adds `bash` before a command if the command name has `.sh`, but that feature does not scan common Git Bash install locations and has no clean fallback when the machine has no bash — it is not reliable enough to depend on.

Because of this, `hooks.json` does not call the hook script directly. It calls `run-hook.cmd` instead — a **polyglot** file that is valid for both `bash` (Unix) and `cmd.exe` (Windows) at the same time, using the `: << 'CMDBLOCK' ... CMDBLOCK` block (`:` is a no-op in bash, so bash skips the whole batch part in between; on Windows, `cmd.exe` only reads the batch part and knows nothing about bash syntax). On Windows, `run-hook.cmd` looks for bash in this order: `PATH` → `C:\Program Files\Git\bin\bash.exe` → `C:\Program Files (x86)\Git\bin\bash.exe` → if none is found, `exit /b 0` (exit quietly, the plugin still works normally, it just misses that hook on a machine with no bash). On Unix, it just runs `exec bash "<hook-dir>/<script-name>" "$@"`.

`hooks.json` calls the wrapper with the syntax `"${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd" <script-name>` plus `"shell": "bash"` — the first argument is the hook script name (no extension), and any later arguments are passed through by the wrapper unchanged.

- `hooks.json` — configures the `SessionStart`, `PreToolUse` (`Edit`/`Write`), and `SubagentStop` hooks, all called through `run-hook.cmd`.
- `run-hook.cmd` — the polyglot wrapper described above.
- `check-protected-paths` — a thin bash entry point; it delegates to `check_protected_paths.py`.
- `check_protected_paths.py` — reads the hook's JSON payload from stdin, blocks (exit 2) a write that matches `rules.paths`, and asks the user for confirmation (exit 0 + JSON `permissionDecision: "ask"` to stdout) when it matches `rules.escalate_paths`. If the project being worked on (read from `payload["cwd"]`) has a `.gft/project.yaml` file (see `templates/project-config.yaml`), the paths in that file's `protected_paths_extra`/`escalate_paths_extra` are **added** to the two lists above — they can only extend the lists, there is no way for project.yaml to weaken or remove a harness rule (no `*_override` field is ever read).
  - **The matching scope differs between the two sources** (fixed after a real false positive was found): a harness pattern (`rules/protected-paths.yaml`, for example `rules/**`/`hooks/**`/`registry/**`) only matches a file that is **really inside the plugin root** (`check-protected-paths` passes `PLUGIN_ROOT` — the parent directory of `hooks/` itself — as argument 2 to the script). If the project using the plugin happens to have a directory with the same name (`rules/`, `hooks/`, `registry/` are very common names for a project's own rule engine/webhook/service registry), the hook does **not** block it by mistake — before this fix it used to block it by mistake, because it matched `file_path` directly against the consuming project's cwd. On the other hand, `protected_paths_extra`/`escalate_paths_extra` in `.gft/project.yaml` still match against the project's own cwd as before, because that path is declared by the project itself to protect its own files.

The confirmation gate for an escalate path is a real `permissionDecision: "ask"` from the Claude Code hook protocol, so the user will see a confirmation prompt before the Edit/Write runs — not just a warning on stderr.

- `check-agent-manifest` / `check_agent_manifest.py` — the `SubagentStop` hook, run when a subagent (`agents/<name>/agent.md`) ends. It compares the `tools:` field in the `agent.md` frontmatter with `allowed_tools` in the matching `manifest.yaml`, and warns on stderr (exit 0, no block) if they do not match. If it cannot tell which subagent just stopped (the payload is missing every identifying key it tried), it skips safely.
  - If the payload has the subagent's transcript path (the field name is also not confirmed for sure by Claude Code, so it tries several candidate keys, the same way it identifies the subagent), the hook also: (1) counts the number of turns and adds up `usage` (input/output/cache tokens) from the transcript, and compares this with `budgets.max_turns` in the manifest; (2) works out which tool groups (`read`/`search`/`write`/`shell`) the agent **actually** called, from the `tool_use` entries in the transcript, and compares this with the maximum group that the declared `authority` allows (for example, `read-only` must not actually use the `write` group) — this is a runtime check, different from the tools-frontmatter-vs-manifest check above (which only compares two static files); (3) finds the most recent report file the agent wrote or edited that matches the `*-report.md` convention (agents/developer/agent.md step 6), then runs the manifest's `verification.command` itself (replacing `<path-to-output.md>` with that path, using `shlex.split` + `subprocess` without a shell, to avoid injection from a path the agent chose itself) and logs PASS/FAIL. If there is no transcript, no report file matching the convention, or the manifest cannot be parsed (`scripts/minimal_yaml.py`) — it skips that part safely, without guessing.
  - All the turns/usage/authority/verification data above is written as one JSON line to `<project-cwd>/.gft/logs/agent-runs.jsonl` (appended), so there is a machine-readable history instead of just a passing warning on stderr.
  - Stricter enforcement steps (hard blocking instead of just warning, checking `budgets.max_recovery_attempts`, checking `authority` against the `allowed_scope`/`risk_tier` of the active task-spec) are noted as TODO right inside `check_agent_manifest.py`, and are not done in this version.

- `session-start` — the `SessionStart` hook (matcher `startup|clear|compact`), it injects the full content of `skills/using-gft/SKILL.md` into the context at the start of the session, through `hookSpecificOutput.additionalContext`. Purpose: the agent checks `registry/activation-rules.yaml` to pick the right agent/skill for the phase **before** acting, instead of guessing or skipping the coordination step — see `skills/using-gft/SKILL.md` for the full injected content. It does not depend on the hook's payload (it does not need to know the `cwd` or which tool just ran), so it has no "skip safely" branch like the other two hooks — if reading fails, it prints the error message inside the injected content itself and still does `exit 0` (it does not block session start).
  - Unlike `check-protected-paths` (hard block) and `check-agent-manifest` (runtime warning only), this hook **checks nothing** — it is only a delivery channel, the same as the user pasting the `using-gft` content at the start of every session by hand, just automated. The part that can be checked is that `skills/using-gft/SKILL.md` only points to `registry/activation-rules.yaml`/`registry/capability-catalog.yaml` — two files that `lint_registry()` (`scripts/validate.sh`) already forces to stay consistent, so the injected content cannot point to an agent/skill that no longer exists without `make validate` catching it first.

To connect this plugin's hooks to another project, add the content of `hooks.json` to that project's `.claude/settings.json`, or load this whole directory as a Claude Code plugin (see the `README.md` at the repo root).

**Important note — a plugin's hooks are only active when the plugin is really "enabled"**, not just because `hooks.json` exists in the directory. Per the Claude Code Hooks Guide, `[Plugin] hooks/hooks.json` is only loaded "when plugin is enabled" — meaning it went through `/plugin install` (or `make install-plugin`) and Claude Code confirmed the plugin is enabled in that session. **Just opening this harness directory directly as a normal project (like when developing straight in the repo) does NOT activate the hooks** — an `Edit`/`Write` into `rules/**`/`manifest.yaml` will not be blocked in that case, even though the `hooks.json` file is in the right place. To test the real hook, install the plugin with `/plugin install gft@gft-harness` (after `/plugin marketplace add`) or run `claude --plugin-dir .` from the repo root, then try an Edit on a protected path to confirm it gets blocked (exit 2).
